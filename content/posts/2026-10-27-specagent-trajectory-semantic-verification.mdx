## 한 줄 요약

**작은 모델이 도구를 쓰며 작업 경로를 만들고, 큰 모델은 중요한 실행 경계에서 그 경로를 검토한다.** SpecAgent는 큰 모델을 매 단계의 작성자에서 검토자로 바꾸는 에이전트 실행 프로토콜이다.

이 글은 [논문 v1](https://arxiv.org/pdf/2610.21463v1)을 기준으로 한다. 아래 수치는 저자들의 실험 결과이며 직접 재현한 결과는 아니다. 마지막의 운영 관점은 논문 설명과 구분해 덧붙였다.

## 1. 조회 한 번에도 가장 큰 모델이 필요한가

주문 환불 에이전트를 생각해 보자. 고객을 찾고, 주문을 조회하고, 환불 조건을 확인한 다음 실제 환불을 실행한다. 모든 단계에서 큰 모델이 다음 도구 호출을 작성하면 단순 조회에도 큰 모델의 생성 비용이 반복된다.

작은 모델로 바꾸면 빠르고 저렴할 수 있지만, 중요한 조건을 놓칠 수 있다. 반대로 작은 모델의 행동을 큰 모델이 매번 다시 작성해 비교하면 절약하려던 작업을 반복하게 된다.

SpecAgent는 다른 질문을 던진다. **큰 모델이 직접 모든 경로를 만들지 않고, 이미 진행된 경로가 유효한지 판단하면 어떨까?** 핵심은 모델 선택 자체보다 역할 분리다. [§1–2](https://arxiv.org/html/2610.21463v1#S1)

## 2. Draft → Verify → Repair

### Draft: 상상한 결과가 아니라 실제 관찰로 진행한다

작은 모델인 Weak는 읽기 도구를 실제 실행한다. 고객 조회 결과에 나온 식별자를 다음 주문 조회에 쓰는 식이다. 여러 미래 호출을 상상해서 한꺼번에 만드는 방식이 아니다.

상태를 바꾸는 행동이 나타나면 그 행동은 **실행하지 않고 보류**한다. 쓰기의 결과를 모르므로 그 이후의 단계도 미리 진행하지 않는다.

### Verify: 정답 문자열 대신 의미를 확인한다

큰 모델인 Strong은 이력과 후보 구간을 읽고, 앞에서부터 어디까지 유효한지 판단한다. 자기 자신이 선택했을 검색어나 조회 순서와 같아야 하는 것은 아니다. 목표를 향한 타당한 행동이면 받아들인다.

검토 결과는 대략 다음 정보를 담는다.

- 승인할 연속된 앞부분의 길이
- 처음 거절한 단계의 이유
- 가능하다면 그 단계를 대체할 행동

중간 오류 뒤의 단계는 앞선 결과에 의존하므로 함께 버린다. 여기서 승인하는 것은 흩어진 개별 단계가 아니라 **연속된 접두 구간(prefix)**이다.

### Repair: 가능한 수정은 검토 응답에 같이 넣는다

틀린 인자 하나를 바꾸는 정도라면 검토 응답에 수정 호출을 포함한다. 이 방식이 fused replacement다. 유효한 대체 호출을 만들지 못하면 Strong이 별도 교정 턴을 수행한다. 교정한 Strong의 행동은 다시 검토하지 않는다.

논문의 환불 예시를 간략화하면 다음과 같다.

```text
Weak
  고객 조회 → 실행하고 결과 확인
  주문 조회 → 실행하고 결과 확인
  환불 정책 조회 → 실행하고 결과 확인
  상품 교환 요청 → 실행 보류
                       │
                       ▼
Strong
  앞의 조회 3단계 승인
  “요청은 교환이 아니라 환불”이라고 판단
  보류한 교환 대신 환불 호출로 교정
                       │
                       ▼
환경에 수정된 행동 반영 → Weak가 다음 작업 재개
```

이는 동작 원리를 보여주는 예시이지, 검토자가 모든 실수를 잡는다는 보장은 아니다. [§3.1–3.2, Figure 1](https://arxiv.org/html/2610.21463v1#S3)

## 3. 놓치기 쉬운 구현 조건

### K개가 쌓였다고 반드시 검토하지 않는다

구간 크기 한도 K에 도달해도 **읽기만 있었다면 검토 없이 이력에 확정하고 계속 진행**한다. 상태 변경 경계를 만났을 때 검토하는 것이 기본 설계다. 따라서 “작은 모델이 여섯 번 행동하면 큰 모델을 한 번 부른다”로 이해하면 정확하지 않다.

### 모든 메시지를 보류하는 것도 아니다

무엇을 상태 변경으로 분류할지는 벤치마크 어댑터에 달려 있다.

| 환경 | 검토 전 보류하는 행동 |
| --- | --- |
| τ²-Bench | 쓰기, 상담 이관 |
| AutomationBench | 쓰기, 최종 메시지 |
| VitaBench | 쓰기 |
| MCP-Atlas | 쓰기, 최종 답변 |

τ²-Bench와 VitaBench의 시뮬레이션 사용자에 대한 대화 응답은 보류하지 않는다. 반면 최종 답변 자체가 평가 대상인 AutomationBench와 MCP-Atlas에서는 답변도 검토한다.

또한 읽기를 이력에서 제거해도 외부 서비스의 접근 로그까지 사라지는 것은 아니다. 논문이 제공하는 실행 경계는 **상태 변경으로 분류된 행동을 검토 전에 실행하지 않는 것**이다. 모든 부수 효과의 롤백이나 검토 결과의 무오류를 보장하는 것은 아니다. [§3.2, Appendix D](https://arxiv.org/html/2610.21463v1#A4)

## 4. 연산이 늘어도 왜 빨라질 수 있을까

LLM 추론에서 prefill은 입력 문맥을 처리하는 단계, decoding은 출력 토큰을 순차적으로 생성하는 단계다.

작은 배치에서 큰 모델의 decoding이 메모리 대역폭에 묶여 있다면, 토큰마다 큰 가중치를 반복해서 읽는 부담이 크다. 반면 후보 경로를 입력으로 읽고 짧은 판정만 생성하면 Strong의 순차 생성량을 줄일 수 있다.

**작성을 검토로 바꾸는 것은 계산을 없애는 것이 아니라, 계산의 형태를 바꾸는 것이다.** Weak의 생성과 Strong의 검토 입력 처리가 추가되므로 FLOPs는 오히려 늘 수 있다.

논문의 비용 모델에서 이득을 좌우하는 조건은 다음과 같다.

- Weak의 초안을 많이 받아들일수록 유리하다.
- 검토 응답이 짧고 별도 교정 턴이 적을수록 유리하다.
- 전체 지연 시간을 줄이려면 Weak의 생성이 Strong보다 충분히 빨라야 한다.
- 큰 배치로 decoding이 연산량 병목에 가까워지면 추가 FLOPs가 부담이 될 수 있다.

이 분석은 작은 decode 배치와 단계 수락 확률 등의 가정을 사용한다. 도구 지연을 생략한 이론식이므로 모든 서비스의 지연 시간을 그대로 예측하는 공식은 아니다. [§3.3, §5](https://arxiv.org/html/2610.21463v1#S3.SS3)

## 5. 실험: 어디까지 품질을 유지했나

주요 실험의 Weak는 Qwen3.5-4B, Strong은 Qwen3.5-397B-A17B다. H20에서 Weak는 GPU 한 장, Strong은 16-way tensor parallelism으로 서빙하고, 각 방식은 작업 8개를 동시 실행했다.

아래는 Table 2에서 단일 모델과 SpecAgent 결과를 추린 것이다. 시간은 작업당 평균 wall time이다.

| 벤치마크 | Weak Pass@1 | Strong Pass@1 | SpecAgent Pass@1 | Strong → SpecAgent 시간 |
| --- | ---: | ---: | ---: | ---: |
| τ² Airline | 80.0% | 86.0% | 86.0% | 305.2 → 126.2초 |
| τ² Retail | 80.4% | 88.6% | 87.7% | 162.4 → 87.5초 |
| AutomationBench | 6.8% | 15.2% | 10.5% | 307.4 → 174.9초 |
| VitaBench Delivery | 34.0% | 48.0% | 44.5% | 197.3 → 135.2초 |

τ²에서는 Strong에 가까운 점수를 유지하며 시간이 크게 줄었다. 그러나 AutomationBench에서는 Strong보다 4.7%p 낮다. “성능 손실 없이 가속한다”는 일반적인 결론은 아니다.

논문의 **품질 격차 회복률**도 절대 성공률과 다르다. AutomationBench에서 회복률은 `(10.5 - 6.8) / (15.2 - 6.8) ≈ 44%`다. 이는 성공률이 44%라는 뜻이 아니다.

τ²의 SpecAgent−Strong 차이에 대한 95% 신뢰구간은 Airline이 −5.3~+5.3%p, Retail이 −4.7~+2.9%p다. 점추정치가 비슷하다는 것과 동등한 성능이 입증됐다는 것은 구분해야 한다.

### 줄어든 자원과 늘어난 자원

- 추정 HBM 읽기 트래픽은 Strong-only 대비 Airline 43–45%, Retail 53–57% 수준으로 줄었다.
- 추정 FLOPs는 Airline 약 30%, Retail과 AutomationBench 약 38%, VitaBench 약 87% 늘었다.
- HBM 트래픽과 FLOPs는 토큰 로그·모델 구조·prefix reuse 가정에 기반한 **추정치**다. HBM 수치를 GPU 메모리 점유량 감소로 읽어서는 안 된다.

비교 방식 중 AgentCollab은 VitaBench에서 50.0%로 SpecAgent의 44.5%보다 높다. 논문의 장점은 모든 품질 순위에서 이긴다는 것이 아니라, 특정 품질·자원 절충점을 보여준다는 데 있다. [§4.1–4.2, Table 2](https://arxiv.org/html/2610.21463v1#S4.T2)

## 6. 로컬 작은 모델 + 클라우드 큰 모델에서는?

MCP-Atlas 실험은 로컬 RTX 5090의 Weak와 클라우드 API의 Strong을 결합한다. 공개 과제 중 별도 비공개 API 키 없이 실행 가능한 101개를 사용했다.

| Strong 모델 | Strong-only 점수 → SpecAgent 점수 | 출력 토큰/작업 | 시간/작업 |
| --- | ---: | ---: | ---: |
| Qwen3.5-397B-A17B | 72.3 → 59.4 | 3.6k → 1.8k | 105 → 120초 |
| GLM-5 | 76.2 → 67.3 | 4.6k → 2.1k | 110 → 108초 |
| DeepSeek-V4-Flash-0731 | 84.2 → 74.3 | 10.6k → 3.8k | 151 → 215초 |

표의 점수는 논문이 Pass@1(%)로 보고한 값이다. 다만 MCP-Atlas의 평가는 LLM judge가 기준 주장 중 얼마나 충족했는지 채점하므로, 앞선 환경의 이진 성공률과 평가 의미가 같다고 가정하지 않는 편이 좋다.

Strong의 출력 토큰은 절반 이하로 줄지만 일관된 속도 향상은 없다. 로컬 Weak가 충분히 빠르지 않아 초안 작성 시간이 더해지기 때문이다. 저자들의 당시 정가 계산에서 클라우드 API 비용은 Strong-only의 59–81%였지만, **로컬 GPU 비용은 제외**했다. 현재 가격이나 전체 운영비 절감률로 해석하면 안 된다. [§4.3, Table 3](https://arxiv.org/html/2610.21463v1#S4.T3)

## 7. 실무에서 가져갈 생각

다음은 논문 실험 결과가 아니라 이 구조를 제품에 적용할 때의 해석이다.

첫째, **모델 라우팅보다 먼저 도구의 실행 경계를 정의해야 한다.** 읽기처럼 보여도 알림 발송이나 외부 상태 변경을 일으키는 도구라면 사후 검토로 되돌릴 수 없다. 도구별 효과와 메시지의 외부 노출 여부를 기준으로 보류 정책을 정해야 한다.

둘째, 의미 검토를 권한 검사와 혼동하지 않아야 한다. Strong이 “타당하다”고 판단해도 권한, 인자 스키마, 업무 규칙을 서버가 강제하는 구조는 별도로 필요하다. 이 논문의 verifier는 형식적 정확성 증명기가 아니다.

셋째, 품질·속도·비용을 각각 측정해야 한다. 도구 응답이 느린 서비스, Weak의 처리량이 낮은 환경, 검토 거절과 재작성이 많은 업무에서는 출력 토큰 감소가 사용자 체감 속도로 이어지지 않을 수 있다.

따라서 도입 판단에는 최소한 작업 성공률, 상태 변경 오류, end-to-end 지연 시간, 초안 수락률, 추가 교정 횟수, 양쪽 모델의 입력·출력 비용이 함께 필요하다. 읽기 결과가 오래된 상태가 되는 동시성 문제도 실제 시스템에서는 따로 다뤄야 한다.

## 정리

SpecAgent의 흥미로운 지점은 **큰 모델의 지능을 어디에 쓸지 다시 정했다**는 데 있다. 모든 단계를 직접 생성하는 대신, 실제 관찰로 만들어진 경로를 검토하고 잘못된 부분만 교정한다.

다만 그 이득은 Weak의 역량, 도구의 읽기·쓰기 구분, 검토 정책, 서빙 병목에 달려 있다. “작은 모델과 큰 모델을 섞으면 싸고 빨라진다”보다 **어떤 행동을 언제 확정하고, 큰 모델이 얼마나 생성해야 하는가**를 설계 문제로 바라보게 하는 논문이다.
