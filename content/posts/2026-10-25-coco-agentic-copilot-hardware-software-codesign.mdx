## 한 줄 요약

Coco는 **새로운 시뮬레이션 데이터를 조회하고, 반복 분석을 도구로 실행하며, 사용자가 보고 있는 화면을 맥락으로 활용하는 하드웨어·소프트웨어 공동 설계용 에이전트 플랫폼**이다.

새로운 LLM이나 학습 알고리즘을 제안하는 논문은 아니다. Google·Google DeepMind·MIT 연구진이 TPU 설계 업무에 적용한 시스템의 구조와 초기 경험을 설명한다. 이 글은 [논문 v1 원문](https://arxiv.org/html/2610.02376v1)을 바탕으로 정리했으며, 뒤의 실무 적용 관점은 논문 결과와 구분해 덧붙였다.

## 1. 아직 존재하지 않는 시스템을 어떻게 분석할까

ML 가속기 설계자는 아직 만들어지지 않은 칩의 성능을 판단해야 한다. 연산 능력, 메모리 용량, 네트워크 구조를 바꿨을 때 모델이 얼마나 빨라질지는 시뮬레이션과 분석 모델로 추정한다.

여러 조건을 바꿔 반복 실행하는 것을 **sweep**이라고 한다. 모델 종류, 배치 크기, 데이터를 여러 장치에 나누는 샤딩 전략까지 조합하면 결과가 빠르게 커진다. 실제 업무의 어려움은 숫자를 얻는 것뿐 아니라 그 숫자가 달라진 이유를 설명하는 데 있다.

- 하드웨어 사양이 달라져서 빨라졌는가?
- 실행 전략이 바뀐 효과인가?
- 특정 모델이나 지연 시간 조건에서만 나타나는 차이인가?
- 실제 하드웨어가 아니라 시뮬레이터의 가정 때문에 생긴 차이인가?

이 데이터는 설계할 때마다 새로 생성된다. 공개 문서를 검색하거나 모델의 사전학습 지식을 꺼내는 것만으로는 답할 수 없다. Coco의 출발점은 **설명에 사용한 수치를 실제 실행 데이터까지 추적할 수 있어야 한다**는 것이다. [논문 §1–2](https://arxiv.org/html/2610.02376v1#S2)

## 2. 네 계층: 데이터, 도구, 에이전트, UI

### 데이터: 파일 묶음을 관계형 데이터로 바꾸기

Coco는 시뮬레이션 결과를 정규화된 관계형 스키마에 등록한다. 워크로드, 시스템, 실행 전략, 지연 시간과 처리량 등의 관계를 공통 구조로 표현하고, 에이전트가 SQL로 조회하게 한다.

중요한 것은 SQL 자체보다 **숫자와 그 숫자를 얻은 절차를 함께 남긴다**는 점이다. 시스템 사양과 모델 설정 같은 설명 자료도 함께 다룬다. 다만 추적 가능한 쿼리가 있다고 해석까지 자동으로 옳아지는 것은 아니다. 잘못된 비교 조건이나 집계 기준은 별도로 검토해야 한다. 이 마지막 구분은 실무적 해석이다.

### 도구: 작은 분석 작업을 명시적인 API로 제공하기

시스템·모델 조합 찾기, 성능 곡선 가져오기, 특정 실행의 상세 내역 조회 등을 문서화된 타입 기반 API로 제공한다. 에이전트는 이 도구들을 조합해 분석한다.

매번 임의의 파일을 뒤지게 하는 대신, 반복되는 작업 단위를 안정적인 도구로 만든 구조다.

### 에이전트: 반복되는 절차와 달라지는 조건 분리하기

분석의 뼈대는 반복되지만 대상 모델, 지연 시간 목표, 비교할 시스템은 달라진다. Coco는 반복 절차를 워크플로로 만들고, 에이전트가 요청별 조건에 맞게 실행하도록 한다.

논문은 여러 지연 시간 목표의 분석을 하위 에이전트로 병렬화하고, 검토 에이전트가 분석의 무결성을 확인한 뒤 오케스트레이터가 보고서를 종합한다고 설명한다. 검토 에이전트의 효과를 별도 수치로 입증한 것은 아니다.

### UI: 사용자의 탐색 상태를 맥락으로 전달하기

사용자가 보고 있는 차트, 선택한 성능 지점, 사용 사례와 시퀀스 길이 조건, 그곳에 도달한 질문의 흐름이 질의에 자동으로 연결된다.

그래서 “이 점은 왜 활용률이 낮지?”라는 짧은 질문에도 분석 대상을 알 수 있다. **UI는 결과를 표시하는 곳이면서 에이전트의 입력을 만드는 곳**이다. [논문 §3](https://arxiv.org/html/2610.02376v1#S3)

## 3. 핵심 분석: 최적 결과만 비교하지 않는다

성능 분석에는 **Pareto frontier**가 자주 등장한다. 지연 시간과 처리량처럼 서로 상충하는 지표에서, 다른 설정에 의해 동시에 밀리지 않는 후보들의 경계다. 더 좋은 대안에 밀린 실행 결과는 이 곡선에 나타나지 않는다.

문제는 시스템마다 최적 실행 전략이 다르다는 것이다. 각 시스템의 최고 결과만 비교하면 하드웨어의 효과와 배치·샤딩 선택의 효과가 섞일 수 있다.

Coco의 **iso-execution analysis**는 특정 지연 시간 목표에서 비교를 시작하고, 같은 샤딩·배치 조건의 대응 결과까지 찾아 상세 분석한다. 이때 Pareto frontier에서 탈락한 실행도 다시 확인한다.

다음은 이해를 위한 예시이며 논문의 측정값이 아니다.

```text
관찰: 시스템 A는 설정 X, 시스템 B는 설정 Y를 선택했다.

추가 질문:
  시스템 B에서도 X를 실행했는가?
  실행했다면 어떤 연산이나 통신 비용 때문에 Y보다 불리했는가?

비교 대상:
  A의 X ↔ B의 X : 같은 실행 조건에서 시스템 차이 확인
  B의 X ↔ B의 Y : 같은 시스템에서 전략 선택의 이유 확인
```

즉, “A가 더 빠르다”에서 끝나는 대신 **왜 B는 A의 전략을 선택하지 않았는가**까지 설명하려는 접근이다. [논문 §3](https://arxiv.org/html/2610.02376v1#S3)

## 4. 논문에 나온 두 사례

### SRAM 확대의 이점은 특정 조건에 집중된다

Ironwood와 TPU 8i의 시뮬레이션 비교에서, 논문은 scratchpad가 128MB에서 384MB로 커지는 효과를 분석한다. 보고된 이점은 특히 **expert 수가 64개 미만이고 지연 시간 제약이 2초 미만인 MoE 조건**에서 나타났다.

저자들의 설명은 단순히 “메모리가 커서 빠르다”가 아니다. 해당 조건에서는 expert 텐서를 SRAM에 유지하고 미리 가져올 수 있는 배치 조합이 가능해지면서 HBM 재읽기가 주요 지연 경로에서 빠진다는 것이다. expert가 더 많거나 지연 시간 제약이 느슨한 경우에는 이 이점이 약해진다고 설명한다.

이는 모든 MoE 모델에 적용되는 일반 법칙이 아니라 **논문이 보고한 분석 조건의 결과**다. [논문 §5.1](https://arxiv.org/html/2610.02376v1#S5.SS1)

### 네트워크 변경 후 병목이 어디로 이동하는가

두 번째 사례는 torus와 Boardfly 네트워크의 what-if 비교다. 배치 크기와 샤딩을 고정하고, expert 병렬 실행에서 발생하는 all-to-all dispatch·combine 통신 지연을 분석한다.

논문은 생성된 타임라인을 통해 병목이 네트워크 중심에서 연산 중심으로 이동하는 모습을 설계자가 확인할 수 있었다고 설명한다. 여기서 핵심은 토폴로지의 우열을 일반화하는 것이 아니라, **조건을 맞춘 비교와 연산별 내역으로 원인을 확인하는 과정**이다. [논문 §5.2](https://arxiv.org/html/2610.02376v1#S5.SS2)

## 5. 무엇이 입증됐고, 무엇이 아직 남았나

논문에 따르면 Coco는 TPU 설계자의 serving 중심 분석에 일상적으로 사용되고 있으며, training과 추가 시뮬레이터 지원을 확대하는 중이다.

그러나 **time-to-simulation과 time-to-insight를 절반으로 줄인다는 수치는 달성 결과가 아니라 목표**다. 본문은 이를 target으로 명시한다. 따라서 “업무 속도를 2배 높였다고 검증한 논문”이라고 소개하면 과장이다.

또한 본문에는 다음을 판단할 충분한 정량 평가가 없다.

- 기존 작업 방식 대비 시간 절감의 표본 수와 분포
- 분석 정확도와 오류율
- 범용 에이전트 대비 성능 차이
- 하위 에이전트·검토 에이전트가 각각 기여한 효과
- 실행 비용과 재현 가능한 평가 조건

이 논문은 대규모 벤치마크보다 **도메인 특화 에이전트의 설계와 초기 운영 경험을 공유하는 글**로 읽는 편이 적절하다. 사례 역시 실물 칩의 독립 측정이 아니라 시뮬레이션 분석으로 구분해야 한다. [논문 §4–5](https://arxiv.org/html/2610.02376v1#S4)

## 6. 내 생각: 화면도 에이전트의 입력이다

여기부터는 논문을 바탕으로 한 적용 관점이다.

가장 인상적인 부분은 멀티에이전트 자체보다 **사용자가 보고 있는 화면을 질문의 일부로 취급한다는 것**이다. 업무용 에이전트가 매번 대상 프로젝트와 선택 조건부터 되묻는다면, 사용자는 일을 맡기기 전에 상황 설명부터 반복해야 한다.

예를 들어 분석 제품의 상세 화면에서 “왜 이 결과가 달라졌지?”라고 물었을 때, 선택한 실행 ID와 비교 대상, 필터 조건이 함께 전달된다면 질문은 짧아져도 분석 범위는 더 명확해질 수 있다. 이는 Coco의 구현을 그대로 재현한 예가 아니라 일반 제품으로 확장해 본 예시다.

또 하나는 **최종 선택뿐 아니라 탈락한 대안도 남겨야 한다**는 점이다. 결과 하나만 저장하면 “무엇이 선택됐는가”는 알 수 있어도 “왜 다른 선택은 안 됐는가”를 설명하기 어렵다. 에이전트가 이유를 설명해야 한다면, 비교 가능한 실행 기록 자체가 중요한 자산이 된다.

결국 Coco에서 가져갈 교훈은 “더 많은 에이전트를 붙이자”보다 다음 세 가지에 가깝다.

1. 숫자를 근거까지 되짚을 수 있게 만든다.
2. 반복되는 분석을 검토 가능한 도구와 절차로 만든다.
3. 사용자의 현재 작업 상태를 에이전트의 입력에 연결한다.

업무용 에이전트의 신뢰는 답변의 유창함뿐 아니라, **무엇을 보고 어떤 비교를 거쳐 그 답에 도달했는지 확인할 수 있는 구조**에서 나온다.
