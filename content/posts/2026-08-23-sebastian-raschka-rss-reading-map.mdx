## 먼저 읽을 글

처음부터 전체 아카이브를 다 읽으려 하면 금방 지친다. 지금 시점에서는 아래 네 묶음부터 보는 게 효율적이다.

### 1. Claude 워터마킹과 AI 텍스트 탐지

- [How Claude Watermarks AI-Generated Text](https://magazine.sebastianraschka.com/p/claude-watermarking)
- [How Claude's Text Watermarking Works](https://sebastianraschka.com/blog/2026/claude-text-watermarking.html)
- [Building an AI Text Detector From Scratch](https://magazine.sebastianraschka.com/p/ai-detector-from-scratch)

이 묶음은 바로 별도 글로 확장하기 좋다. 핵심 질문은 “AI가 쓴 글을 기술적으로 식별할 수 있는가?”다.

워터마킹은 모델이 토큰을 샘플링할 때 특정 통계적 패턴을 남기는 방식이다. 탐지기는 반대로 텍스트의 분포, perplexity, token-level signal을 보고 생성 여부를 추정한다. 둘 다 그럴듯하지만, 실무적으로는 항상 같은 문제가 따라온다.

- paraphrasing을 거치면 신호가 얼마나 남는가
- 다른 모델로 rewrite하면 탐지율이 어떻게 바뀌는가
- 짧은 텍스트에서도 안정적으로 작동하는가
- false positive를 조직 정책에 사용할 수 있을 만큼 낮출 수 있는가

내가 보기에는 이 주제는 “탐지기가 가능하냐 아니냐”보다 “탐지 결과를 어떤 의사결정에 쓰면 위험한가” 쪽이 더 중요하다. 학교나 채용, 평가처럼 개인에게 불이익을 주는 영역에서는 탐지 점수 하나로 판단하면 안 된다. 반대로 내부 콘텐츠 품질 관리나 synthetic data 필터링처럼 보조 신호로 쓰는 영역에서는 꽤 유용할 수 있다.

## 2. 오픈웨이트 LLM 아키텍처 읽기

Raschka 글의 가장 큰 장점은 모델 발표를 아키텍처 관점으로 해부한다는 점이다. 특히 최근 글은 “요즘 큰 모델들이 어디서 효율을 짜내는가”를 따라가기 좋다.

먼저 볼 글은 이쪽이다.

- [Muse Glimmer 30B Architecture Notes](https://sebastianraschka.com/blog/2026/muse-glimmer-30b-architecture-notes.html)
- [Kimi K3 Architecture Notes](https://sebastianraschka.com/blog/2026/kimi-k3-architecture-notes.html)
- [Inkling: A New Open-Weight 975B MoE with a Few Surprises](https://sebastianraschka.com/blog/2026/inkling-architecture-benchmark-notes.html)
- [GLM-5.2 and IndexShare for Long-Context Sparse Attention](https://sebastianraschka.com/blog/2026/glm-5-2-indexshare.html)
- [MiniMax M2 Technical Report Notes](https://sebastianraschka.com/blog/2026/minimax-m2-technical-report.html)
- [DeepSeek Sparse Attention From Scratch](https://sebastianraschka.com/blog/2026/deepseek-sparse-attention-from-scratch.html)

이 글들을 하나씩 보면 모델 이름은 다르지만 반복되는 패턴이 보인다.

### Attention은 점점 더 비싸게 쓰지 않는다

긴 context를 그대로 dense attention으로 처리하면 비용이 빠르게 커진다. 그래서 sparse attention, compressed attention, KV sharing, local/global attention 혼합 같은 방식이 계속 나온다. 핵심은 모든 토큰이 모든 토큰을 같은 강도로 볼 필요가 없다는 것이다.

실무적으로는 이 관점이 중요하다. 긴 문서를 넣을 수 있다는 것과 긴 문서를 잘 읽는다는 것은 다르다. 모델이 어떤 attention 구조를 쓰는지에 따라 긴 context에서 강한 작업과 약한 작업이 갈린다.

### MoE는 parameter 수보다 routing 품질이 중요해진다

MoE 모델은 겉으로는 거대한 parameter 수가 눈에 띈다. 하지만 실제 추론 비용은 active parameter와 routing 방식에 좌우된다. 전문가를 많이 둔다고 자동으로 좋은 모델이 되는 게 아니라, 어떤 토큰을 어떤 expert에 보낼지, expert load를 어떻게 균형 맞출지, long-context나 multimodal 입력에서 routing이 흔들리지 않는지가 중요하다.

그래서 MoE 글은 “몇 B 모델인가”보다 “active parameter, expert routing, memory bandwidth, serving 효율”을 중심으로 읽어야 한다.

### KV cache는 serving 비용의 중심이다

요즘 모델 아키텍처에서 KV cache 최적화가 자주 등장하는 이유는 단순하다. 실제 서비스에서는 prefill보다 decode가 길어지고, concurrent user가 많아지고, context도 길어진다. 이때 KV cache가 메모리를 잡아먹는다.

따라서 GQA, MQA, KV sharing, latent attention, cache compression 같은 기법은 논문 장식이 아니라 운영 비용과 직결된다. “이 모델이 싸게 서빙될 수 있는가”를 보려면 benchmark 점수만 보면 안 되고 KV cache 구조를 같이 봐야 한다.

## 3. Reasoning effort와 inference-time scaling

다음 묶음은 reasoning이다.

- [Controlling Reasoning Effort in LLMs](https://magazine.sebastianraschka.com/p/controlling-reasoning-effort-in-llms)
- [Categories of Inference-Time Scaling for Improved LLM Reasoning](https://magazine.sebastianraschka.com/p/categories-of-inference-time-scaling)
- [Understanding Reasoning LLMs](https://magazine.sebastianraschka.com/p/understanding-reasoning-llms)

요즘 reasoning 모델을 볼 때 중요한 질문은 “생각을 많이 하면 좋아진다”가 아니다. 더 정확한 질문은 이렇다.

- 어떤 문제에서 더 긴 reasoning이 실제로 성능을 올리는가
- 어느 지점부터는 token 낭비가 되는가
- 사용자가 low, medium, high effort를 선택할 수 있어야 하는가
- latency budget이 있는 production system에서는 어떻게 effort를 배분해야 하는가

reasoning effort 제어는 제품 설계 문제이기도 하다. 모든 요청에 최고 effort를 쓰면 비용과 latency가 터진다. 반대로 모든 요청을 cheap mode로 처리하면 어려운 문제에서 품질이 무너진다.

내가 선호하는 방향은 요청을 세 단계로 나누는 것이다.

1. **기본 응답**: 검색이나 복잡한 reasoning 없이 바로 답할 수 있는 요청
2. **검증형 응답**: 계산, 파일, 코드, 최신 정보처럼 tool 확인이 필요한 요청
3. **고난도 reasoning**: 설계, 디버깅, 논문 해석, multi-step planning처럼 깊게 생각해야 하는 요청

모델이 reasoning mode를 제공하더라도 harness가 이 routing을 못 하면 실무 효과는 반감된다. 결국 reasoning model 자체보다 “언제 깊게 생각하게 할 것인가”가 더 중요해진다.

## 4. 로컬 coding agent와 open-weight 모델

coding agent 쪽에서는 아래 글이 좋다.

- [Using Local Coding Agents](https://magazine.sebastianraschka.com/p/using-local-coding-agents)
- [Local Open-Weight LLMs in Coding Harnesses](https://sebastianraschka.com/blog/2026/local-open-weight-llms-coding-harnesses.html)
- [Components of A Coding Agent](https://magazine.sebastianraschka.com/p/components-of-a-coding-agent)

이 묶음의 핵심은 “모델만 로컬로 바꾸면 coding agent가 되는가?”다. 답은 아니다.

coding agent 품질은 모델 하나로 결정되지 않는다. 최소한 아래 구성요소가 같이 필요하다.

- repo index와 파일 검색
- patch 적용 방식
- test runner와 실패 로그 요약
- tool call 권한 관리
- context 압축과 memory
- rollback과 diff review

open-weight 모델을 local coding harness에 붙이는 것은 비용과 privacy 측면에서 매력적이다. 하지만 작은 모델일수록 harness 품질의 영향을 더 크게 받는다. 좋은 harness는 모델의 약점을 보완하고, 나쁜 harness는 강한 모델도 삽질하게 만든다.

그래서 로컬 coding agent를 평가할 때는 “HumanEval 몇 점”보다 실제 repo에서 다음을 봐야 한다.

- 기존 코드 스타일을 따라가는가
- 작은 수정에서 과도한 rewrite를 하지 않는가
- test failure를 읽고 원인을 좁히는가
- 파일을 잘못 건드렸을 때 복구할 수 있는가
- 긴 작업에서 목표를 잃지 않는가

## 이 RSS를 앞으로 어떻게 쓸 것인가

이 RSS는 세 가지 용도로 쓰면 좋다.

### 1. 아키텍처 변화 감지기

새로운 오픈웨이트 모델 글이 올라오면 먼저 architecture note로 읽는다. 그리고 다음 질문으로 분류한다.

- attention 변형이 있는가
- KV cache 최적화가 있는가
- MoE routing 변화가 있는가
- long-context 처리 방식이 특이한가
- serving 비용을 줄이는 구조가 있는가

이 중 하나라도 뚜렷하면 별도 글 후보가 된다.

### 2. Reasoning 제품 설계 힌트

reasoning 관련 글은 모델 성능보다 제품 동작 방식에 연결해서 읽는다.

- effort mode를 사용자에게 노출할 것인가
- 자동 routing으로 숨길 것인가
- tool-use와 reasoning을 어떻게 섞을 것인가
- 평가 기준을 정답률, latency, 비용 중 어디에 둘 것인가

이건 agent 제품이나 내부 자동화 시스템을 만들 때 바로 설계 의사결정으로 이어진다.

- 실무자가 의사결정에 쓸 수 있는 takeaway가 있다
- primary source나 논문, technical report로 더 깊게 확인할 수 있다
